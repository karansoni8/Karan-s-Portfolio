What fired

A Sysmon process-access event involving lsass.exe can be worth investigating. Granted access, source process, signer information and surrounding events all matter; one event alone does not prove credential dumping.

The rule

event.code : "10"
  and winlog.event_data.TargetImage : "*\\lsass.exe"
  and winlog.event_data.GrantedAccess : ("0x1010" or "0x1410" or "0x143a")
  and not process.executable : ("*\\MsMpEng.exe" or "*\\wmiprvse.exe")

What tuning taught me

This example focuses on access masks and known legitimate processes. In a real environment I would verify event fields, inspect signatures and baseline benign behavior before creating exclusions; broad process-name exclusions can hide abuse.

What fired

Encoded PowerShell from an Office or script-host parent is worth investigating. The encoded flag is not malicious by itself; parent process, command contents and subsequent activity provide necessary context.

The rule

process.name : "powershell.exe"
  and process.command_line : ("*-enc*" or "*-EncodedCommand*")
  and process.parent.name : ("winword.exe" or "excel.exe"
                             or "outlook.exe" or "wscript.exe")

Why the parent matters

Parent-process context helps prioritize potentially suspicious executions. The query is an illustrative starting point; benign administrator activity and process field mappings require validation before deployment.

What fired

Same internal host, same external IP, connections about every 60 seconds with very little variance and near-identical payload sizes.

Analysis outline · pseudocode, not executable KQL

1. Filter Zeek connection records for a source/destination pair
2. Sort connections by timestamp
3. Calculate inter-arrival intervals
4. Compare interval variance and connection counts
5. Validate against benign polling and scheduled jobs

Why network data

Network telemetry can complement endpoint records, including when a target has no endpoint agent. Periodicity is a lead, not proof of command and control; confirm with destination reputation, context and packet-level evidence.

What this is

An example investigation sequence in a controlled environment, showing how events change an analyst’s interpretation and response priority.

T+00:00
Macro-borne execution on a workstation

Sysmon EID 1 shows winword.exe spawning powershell.exe with an encoded command. The parent-process rule fires within seconds.

→ Confirmed true positive, isolate host
T+00:04
Discovery, quiet and unalerted

The shell enumerates domain users and local groups. Nothing fired: I had the telemetry but no rule. Discovery needs volumetric rules, not signatures.

→ Documented as detection gap
T+00:11
Credential access on the domain controller

A handle opens against lsass.exe with dump-capable access rights. At this point it stops being a workstation problem.

→ Escalate, assume domain credentials exposed
T+00:19
Lateral movement over SMB

Zeek shows admin-share access to a second host minutes after the credential theft. The SMB session alone would have been ambiguous; the sequence isn't.

→ Contain both hosts, force credential reset
T+01:30
Write-up and rule changes

Documented the chain, added the missing discovery rule, and re-ran the same attack to confirm it fired.

→ One new rule, one tuned, one gap closed

Telemetry reaching the SIEM Network data only — no endpoint agent

A conceptual view of how lab telemetry reaches Elastic. The dashed line is the gap I found the hard way: Metasploitable is Linux and never got an agent, so when I ran the SMB exploit against it, Zeek saw the traffic and the endpoint side saw nothing at all.

Security Onion runs in EVAL mode because of RAM limits. Zabbix monitoring broke early on from DHCP-driven IP drift, which is how I learned to pin the monitored hosts.

Microsoft Sentinel lab

Design-stage project: a controlled password-spray detection in Microsoft Sentinel. This is planned work, not a completed deployment or production experience.

  1. Simulated attackControlled failed sign-ins
  2. Windows eventsSecurity Event 4625
  3. AMA + DCRCollect and route
  4. Analytics ruleGroup by account and IP
  5. IncidentEntities, triage and evidence

Proposed detection

SecurityEvent
| where TimeGenerated > ago(15m)
| where EventID == 4625
| where isnotempty(IpAddress) and IpAddress != "-"
| summarize FailedAttempts=count()
    by Account, IpAddress, bin(TimeGenerated, 5m)
| where FailedAttempts >= 10

Build and proof plan

  • Connect an isolated Windows test VM through Azure Monitor Agent and a Data Collection Rule.
  • Confirm the expected fields arrive in the SecurityEvent table.
  • Generate controlled failures, tune the threshold and document normal noise.
  • Create the scheduled analytics rule, map account and IP entities, then verify the incident timeline.
  • Publish screenshots and results only after the test is repeatable.

Why it is marked planned: the architecture and query are ready to build, but no production claim is made until ingestion, detection and incident creation are verified end to end.
