Elastic SIEM · lab.internal5 open

What fired

A process opened a handle to lsass.exe with read-memory access rights. That call pattern is what credential dumpers need and almost nothing legitimate does — which is why it's worth alerting on, and why it's noisy if written lazily.

The rule

event.code : "10"
  and winlog.event_data.TargetImage : "*\\lsass.exe"
  and winlog.event_data.GrantedAccess : ("0x1010" or "0x1410" or "0x143a")
  and not process.executable : ("*\\MsMpEng.exe" or "*\\wmiprvse.exe")

What tuning taught me

The first version fired 40+ times a day on Defender and WMI alone. Filtering on granted-access masks instead of process name cut the noise without blinding the rule to a renamed dumper — the mask is behaviour, the name is a string the attacker controls.

What fired

PowerShell launched with -enc and a base64 blob. Encoding isn't malicious on its own — plenty of management tooling does it — so the rule scores on parent process rather than the flag alone.

The rule

process.name : "powershell.exe"
  and process.command_line : ("*-enc*" or "*-EncodedCommand*")
  and process.parent.name : ("winword.exe" or "excel.exe"
                             or "outlook.exe" or "wscript.exe")

Why the parent matters

An Office app spawning an encoded shell is the phishing macro chain in one line. Scoping to those parents took a rule that couldn't ship down to zero false positives across two weeks of lab traffic.

What fired

Same internal host, same external IP, connections landing roughly every 60 seconds with very little variance and near-identical payload sizes. Humans don't browse like that. Implants do.

How I found it

zeek.session_id : *
  and network.protocol : "http"
  | stats count(), stddev(interval) by source.ip, destination.ip
  | where stddev < 5 and count() > 30

The point

This one doesn't come from an endpoint agent at all. Network telemetry catches what a compromised host would happily lie about — the argument for running Zeek alongside Sysmon rather than picking one.

What this is

A single simulated intrusion I ran end to end, in the order I actually saw it. Individual rules are table stakes. Connecting them into one story, and knowing what to do at each step, is the job.

T+00:00
Macro-borne execution on a workstation

Simulated phishing document runs a macro. Sysmon EID 1 shows winword.exe spawning powershell.exe with an encoded command. The parent-process rule fires within seconds.

Confirmed true positive — isolate host
T+00:04
Discovery, quiet and unalerted

The shell enumerates domain users and local groups. Nothing fires — I had telemetry but no rule. This is where I learned discovery activity needs volumetric rules, not signature rules.

Documented as detection gap
T+00:11
Credential access on the domain controller

A handle opens against lsass.exe with dump-capable access rights. In a real environment this is the moment the incident stops being a workstation problem and becomes a domain problem.

Escalate — assume domain credentials exposed
T+00:19
Lateral movement over SMB

Zeek shows admin-share access to a second host minutes after the credential theft. The sequence is what makes it conclusive — the SMB session alone would have been ambiguous.

Contain both hosts — force credential reset
T+01:30
Write-up and rule changes

Documented the chain, added the missing discovery detection, and re-ran the same attack to confirm the new rule fired. An incident that doesn't change your detections was a wasted incident.

One new rule, one tuned, one gap closed
